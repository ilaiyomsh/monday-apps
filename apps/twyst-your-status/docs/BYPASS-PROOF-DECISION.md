# עמידות לעקיפה — מסמך החלטה

**אפליקציה:** twyst-your-status (App ID 11775054, `AppFeatureStatusColumn`, client-only CDN)
**תאריך:** 2026-08-03 · **סטטוס:** ממתין להחלטת בעלים — טרם החל מימוש
**טריגר:** סרטון מלוח לקוח (ministry-of-the-environmental, לוח "טיוטת יעדים 27") שבו בטעינה קרה של הלוח העמודה מתנהגת כעמודת סטטוס רגילה למשך ~5–15 שניות, והבורר הנייטיבי נפתח עם כל הלייבלים ו-Edit Labels — עקיפה מלאה של כללי האפליקציה.

**מתודולוגיה:** מחקר רב-סוכני — קריאת קוד הריפו, אימות מול מאגר הידע הרשמי של monday וסכמת ה-GraphQL, מיפוי משטחי עקיפה, ובחינה אדברסרית של שלוש ארכיטקטורות מועמדות (13+ התקפות לכל אחת). כל קביעה במסמך מסומנת ✅ (מאומת), 🔶 (סביר, טעון אימות), או ❓ (לא ידוע).

## 1. תקציר מנהלים

1. **את חלון הטעינה אי אפשר לסגור מצד ה-client.** בזמן החלון לאפליקציה אין אף שורת קוד בדף — העיכוב הוא שכבת ה-bootstrap של הפיצ'רים של monday עצמה. שום preload / הקטנת bundle / service worker לא נוגעים בו. לפלטפורמה אין מתג "חסום עריכה נייטיבית עד שהאפליקציה נטענת" (✅ נבדק מול הדוקומנטציה; אין גם known issue מתועד).
2. **חלון הטעינה הוא אחד מ~15 משטחי עקיפה, ורובם פתוחים תמיד** — מובייל (פיצ'רים של עמודות לא נטענים שם בכלל), כרטיס פריט, קנבן, פעולות מרובות, הדבקת תאים, My Work, דשבורדים, טפסים, ייבוא אקסל, Undo מיומן הפעילות, טוקן API אישי, אוטומציות ואינטגרציות. ה-MANIFEST של האפליקציה עצמו מודה בפער ("Limits").
3. **ליקוי חמור נוסף שהתגלה אגב המחקר:** הכללים שמורים ב-monday.storage בסקופ global — **כל משתמש בחשבון יכול לשכתב אותם** (אין ACL פר-משתמש). כל פתרון אכיפה חייב קודם להפוך את הכללים לסמכות-שרת.
4. **ההמלצה: פתרון תלת-שכבתי** — (0) כללים בצד שרת; (1) "שומר" מבוסס webhook שמאמת כל שינוי ומחזיר שינויים לא חוקיים תוך שניות, על כל תוכנית ועל כל משטח; (2) ללוחות שדורשים מניעה מוחלטת — נעילת ‏"Restrict column editing" הנאכפת בליבת monday (כולל API וכולל בחלון הטעינה) + שער כתיבה בשרת. הבחינה האדברסרית אישרה שהשילוב עומד, בכפוף לתנאים שבסעיף 7.
5. **הקשר שוק:** הפיצ'ר הנייטיבי היחיד שדומה ("Conditional status changes", ‏CRM/Service Ultimate בלבד) **מוצא משימוש ביוני 2026** — הפלטפורמה מפנה בדיוק את המגרש הזה. אין ולא צפוי מתג נייטיבי שיפתור את זה בשבילנו. (✅)

## 2. הבעיה שנצפתה ושורשה

בסרטון: טעינה קרה → ~10 שניות שלד → הטבלה נטענת אבל שכבת הפיצ'רים טרם נקשרה → קליק על תא בעמודה המנוהלת פותח את **העורך הנייטיבי** (כל 5 הלייבלים + Edit Labels) → רק ~5 שניות אחר כך אותו קליק נפתח דרך ה-iframe של האפליקציה (3 אפשרויות מסוננות).

השורש: פיצ'ר `AppFeatureStatusColumn` הוא **קישוט** על עמודת סטטוס אמיתית. עד ששכבת הפיצ'רים של monday עולה (placement ‏`columnPickers`), העמודה היא עמודת סטטוס רגילה לכל דבר. הקישוט מוחלף רק במשטח אחד: קליק על תא בטבלת הלוח, בדסקטופ-web, אחרי ה-bootstrap.

## 4. שני ליקויים קיימים שחובה לתקן בכל מסלול

1. **הכללים ניתנים לשכתוב ע"י כל משתמש בחשבון.** ‏`twystStatus:<boardId>:<columnId>` נשמר ב-`monday.storage` בסקופ global (app+account), ללא בקרת גישה פר-משתמש — כל מי שמריץ את האפליקציה בחשבון יכול `setItem` של קונפיגורציה מתירנית. ה-MANIFEST מודה בזה (סעיף Limits). כל עוד זה כך, גם "שומר" מושלם מאמת מול כללים שהתוקף שולט בהם. (✅)
2. **חתימת כתיבה לגיטימית אינה אפשרית מצד client:** כל נונס/סימון שהבורר ישאיר ב-storage ניתן לזיוף מאותה סיבה. מכאן שהוולידציה חייבת להתבצע בשרת, מול עותק כללים שרק השרת כותב.

## 5. מה הפלטפורמה נותנת ומה לא (עובדות מאומתות)

**אין:**
- מתג להשבתת העורך הנייטיבי בזמן טעינת הפיצ'ר, או "עורך בלעדי". (✅)
- API לקריאה/כתיבה של column permissions — הקמה ידנית בלבד ב-UI. (✅)
- "app actor": כל מוטציה ב-API רצה בהקשר של משתמש אמיתי; אין זהות-אפליקציה שכותבת ללוח. (✅)
- הגבלת בחירת לייבלים נייטיבית: ‏Managed Columns נועל את **הגדרות** הלייבלים, לא את בחירת הערכים; "Conditional status changes" קיים רק ב-CRM/Service Ultimate ומוצא משימוש 6/2026. (✅)

**יש:**
- **"Restrict column editing"** ‏(Pro + Enterprise): נאכף בליבת monday בצד שרת, **כולל מול טוקני API** (הטוקן משקף את הרשאות ה-UI) — ולכן תקף גם בתוך חלון הטעינה. בעלי לוח לעולם אינם מוגבלים. זה אותו 🔒 שכבר קיים על שתי עמודות שכנות בלוח של הלקוח. (✅)
- **Webhook פר-עמודה:** ‏`change_status_column_value` (או `change_specific_column_value` עם `{"columnId":…}`); ה-payload כולל `userId` (מי שינה), `previousValue` ו-`value` — בדיוק הקלט לוולידציית מעבר. רישום דרך `create_webhook` ‏(scope ‏`webhooks:write`), עם challenge handshake. ‏Retry לכשל מסירה: פעם בדקה למשך 30 דקות. זמן מסירה ראשונה אינו מתועד. (✅)
- **Storage משותף לשרת:** רכיב monday-code של **אותה אפליקציה** חולק את מרחב ה-storage (הפרדה לפי accountId+app). (🔶 — לאמת ב-probe; אם לא, מסך ההגדרות משקף את הכללים לשרת בשמירה.)
- אוטומציות רצות בהרשאות **יוצר האוטומציה**. (✅)

## 7. הפתרון המומלץ — פירוט

### שכבה 0 — הכללים עוברים לסמכות-שרת (תנאי לכל השאר)

- מקימים רכיב monday-code ל-twyst (אותו App ID → אותו מרחב storage; האפליקציה הופכת client+server כמו deadline-confirm).
- הכללים נכתבים מהשרת בלבד (SecureStorage עם prefix ‏`${accountId}:`), אחרי אימות sessionToken שהפונה הוא בעל לוח. מסך ההגדרות עובר לכתוב דרך endpoint במקום `monday.storage.setItem`.
- ה-client ממשיך **לקרוא** עותק תצוגה מה-storage הרגיל (מהירות הבורר לא נפגעת) — אבל האכיפה מאמתת רק מול עותק השרת.

### שכבה 1 — השומר (כל התוכניות, כל המשטחים)

- רישום `change_status_column_value` פר עמודה מנוהלת (אוטומטית בשמירת הגדרות) + `create_item`/`create_pulse` לכיסוי משטחי יצירה (טפסים, שכפול, ייבוא).
- על כל אירוע: אימות challenge/JWT → אם המשנה הוא זהות-השירות: התעלמות (loop guard) → ולידציה מול כללי השרת: הרשאות פר-לייבל, חברות בצוותים, מעברים (`previousValue` מה-payload הוא המקור; כולל כלל המצב הריק, מפתח 5), נוכחות שדות חובה (קריאת item) → שינוי פסול: החזרה ל-`previousValue` ככתיבת זהות-השירות + הודעה למשתמש (notification) עם הסיבה.
- הגנות: סריאליזציה פר-item (שינויים מהירים ברצף), circuit breaker פר-item (מלחמת-החזרות מול אוטומציה), תור עם קצב (bulk paste של 200), התראות בריאות ל-Axiom (`app-errors`), ניטור תוקף הטוקן.
- **גבולות שמוצהרים ביושר:** הערך הפסול גלוי שניות בודדות עד ההחזרה; שרת מושבת = אין אכיפה (fail-open); אוטומציה שמופעלת מהערך החולף עלולה להספיק לירות.

### שכבה 2 — מניעה קשיחה (Pro/Enterprise, פר לוח לפי דרישה)

- בעל הלוח מפעיל ידנית "Restrict column editing" על העמודה, ומשאיר מורשה יחיד: **משתמש-שירות ייעודי** (member seat שאינו בעל לוח — בעלים פטורים מהנעילה).
- הבורר מזהה עמודה נעולה ועובר לכתוב דרך endpoint‏ `/write`: השרת מאמת (אותו מודול ולידציה של שכבה 1) וכותב כזהות-השירות. העורך הנייטיבי בכל משטח — כולל חלון הטעינה, מובייל וטוקנים אישיים — נחסם ע"י ליבת monday.
- כשל שרת = fail-closed (אי אפשר לשנות סטטוס עד שהשרת חוזר) — לתעד כתכונה מכוונת של מסלול זה.
- ייחוס: יומן הפעילות ירשום את זהות-השירות; המשתמש האמיתי יתועד ב-update על הפריט או בלוג ייעודי.

### מה כל שכבה סוגרת

| משטח | היום | שכבה 1 | שכבה 2 |
|---|---|---|---|
| חלון טעינה קרה | פתוח | החזרה תוך שניות | **חסום** |
| מובייל / כרטיס פריט / קנבן / bulk / הדבקה / My Work / דשבורדים | פתוח | החזרה תוך שניות | **חסום** |
| API בטוקן אישי / אינטגרציות | פתוח | החזרה תוך שניות | **חסום** |
| אוטומציות | פתוח | החזרה + circuit breaker | חסום (אלא אם היוצר הוא בעל לוח) |
| טפסים / שכפול / ייבוא (יצירה) | פתוח | החזרה (webhook יצירה) | החזרה (❓ אם הנעילה חלה ביצירה — לאמת) |

| עטיפות SecureStorage עם retry/caching (+ מלכודת unwrap של 0.1.4) | שלוש אפליקציות השרת |
| מודול הוולידציה (allowlists, מעברים, מצב ריק, שדות חובה) | **קיים היום ב-client** — `src/domain/` טהור וניתן לחילוץ לחבילה משותפת client+server |
| CI/CD לאפליקציית שרת | תבניות deploy-draft/live קיימות; onboarding דרך monday-cicd |

## 9. עלויות ודרישות

- **פיתוח (הערכה גסה בסבבים):** שכבה 0+1 — סבב גדול אחד או שניים (שרת חדש + webhook + חילוץ ולידציה משותפת + בדיקות); שכבה 2 — סבב בינוני נוסף (endpoint כתיבה + מיתוג בבורר + נוהל הקמה).
- **תפעול:** ‏seat למשתמש-השירות; מכסת monday-code; תקציב complexity לקריאות הוולידציה וההחזרות.
- **הקמה פר לוח:** רישום ה-webhook אוטומטי; נעילת העמודה (שכבה 2) ידנית ע"י בעל הלוח — נספק צ'ק-ליסט מסך-הגדרות שמזהה עמודה לא נעולה ומנחה.
- **דרישות תוכנית:** שכבה 1 — כל תוכנית; שכבה 2 — Pro/Enterprise (הלקוח שבסרטון: Enterprise ✅).

## 11. המלצה

לאשר את המסלול ההיברידי המדורג: **שכבה 0 + שכבה 1 לכלל הלוחות** (סוגר את הסרטון ואת כל משפחת העקיפות תוך שניות, בלי שינוי UX), ו**שכבה 2 כאופציה פר-לוח** ללקוחות שדורשים מניעה מוחלטת — ובראשם הלוח שבסרטון, שכבר משתמש בנעילות עמודה ולכן ההקמה הידנית טבעית לו. לפני המימוש — לסגור את שאלות סעיף 10 (probe בסנדבוקס + בדיקה חיה עם תוסף הדפדפן).
