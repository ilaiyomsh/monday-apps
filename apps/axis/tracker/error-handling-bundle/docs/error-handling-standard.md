# סטנדרט טיפול בשגיאות — Tracker

מסמך זה מגדיר מתי מקור שגיאה בקוד נחשב **מטופל**. הוא הסרגל שמולו עוברים על כל אתר בקוד שעלול להיכשל, והקלט הרשמי לוורקפלו הביקורת.

> הערה: מסמך זה אינו מסתמך על `Implementing_7_Layer_Error_Handling_System.md` (שלא עבר בקרה). הוא מבוסס על עקרונות מקובלים בתעשייה, מעוגנים בכלים האמיתיים של הפרויקט: `logger`, `parseMondayError` / `MondayApiError`, ו־`showErrorWithDetails`.

---

## 1. מה נחשב "מקור שגיאה" (= שורה בטבלה)

כל אתר בקוד שעלול להיכשל:

1. כל `await` של פעולה אסינכרונית — קריאת API, `monday.storage`, `monday.get`.
2. קריאות SDK ישירות — `monday.api`, `monday.execute`, `monday.listen`.
3. פענוח נתונים חיצוניים — `JSON.parse`, גישה לשדות בתשובת API שעלולה להיות חסרה (`res.data.boards[0]...`).
4. `useEffect` שמשגר עבודה אסינכרונית — סיכון ל־race / `setState` אחרי unmount.
5. event handlers שקוראים לפעולה אסינכרונית.
6. קוד שרץ בזמן render ועלול לזרוק — null deref על props/state.
7. פענוח תאריך/מספר — `new Date()`, `parseFloat`, `parseInt` על קלט לא ודאי.

בנוסף, נבדקות שתי תשתיות גלובליות כפריט ייעודי:

- **רשת ביטחון גלובלית** — `window.onerror` ו־`window.addEventListener('unhandledrejection')`.
- **`ErrorBoundary`** — קיום גבול שגיאות ב־React שמונע הלבנת מסך.

## 2. ממדי הציון (= עמודות הטבלה)

| עמודה | ערכים אפשריים |
|-------|----------------|
| מיקום | `קובץ:שורה` |
| פעולה | מה הקוד עושה |
| קטגוריה | API / render / רשת / race / לא־נתפסת / ולידציה / SDK |
| נתפס? | לא / `try-catch` / `.catch` / wrapper / ErrorBoundary |
| נרשם? | נבלע / רק `console` / `logger.error` / `logger.apiError` / `logger.warn` |
| מוצג למשתמש? | לא / toast / inline / fallback UI / לא־רלוונטי (רקע) |
| ברור? | ממופה דרך `parseMondayError` / הודעה גנרית / אטום |
| חומרה | קריטי / גבוה / בינוני / נמוך |
| פסק דין | תקין / פער (+ סוג הפער) |
| תיקון מוצע | תיאור קצר של התיקון הנדרש (לא מיושם — לאישור) |

## 3. הגדרת "תקין" (PASS) — חייב לעמוד בכל הארבעה

1. **כיסוי** — הכשל נתפס במנגנון המתאים לקטגוריה שלו: `try/catch` סביב `await` באסינכרוני; `ErrorBoundary` ל־render; handler גלובלי לבורחות; abort/guard ל־race.
2. **אפס בליעה שקטה** — בנתיב הכשל יש קריאה ל־`logger` (באחת הרמות) עם מודול + הודעה + אובייקט השגיאה. `catch` ריק, `catch {}`, או `catch` שרק מחזיר ברירת מחדל / משנה UI בלי לרשום = **פסילה אוטומטית**.
3. **בהירות** — לשגיאה יש זהות: קוד/קטגוריה (דרך `parseMondayError` / `MondayApiError`), ובמקום שפונה למשתמש — הודעה ספציפית בעברית + `actionRequired`, ולא fallback גנרי.
4. **הצגה למשתמש כשרלוונטי** — ראה סעיף 5.

---

## 4. כלל הבליעה השקטה

כל `catch` / `.catch` חייב לכלול קריאה ל־`logger`. בלי זה — פער, גם אם השגיאה "צפויה" וזניחה ("זניח" זו החלטה שמותר לקבל רק אחרי שרואים את השגיאה, לא במקומה).

**החריג היחיד — ביטול מכוון:**

```js
} catch (e) {
    if (e.name === 'AbortError') return;   // ביטול מכוון — לא לרשום כשגיאה
    logger.error('Module', 'נכשל', e);
}
```

**`console` עירום** — קוד שתופס ומדפיס ב־`console.log` / `console.error` ישיר במקום `logger`: אינו בליעה (השגיאה visible), אך **פער "נמוך"** — לא יעבור ל־sink העתידי ונוגד את קונבנציית הפרויקט. מסומן בעמודת "נרשם?" כ"רק `console`".

---

## 5. הצגה למשתמש — מותנה בהשפעה

| המצב | חובה הצגה? | אם לא מוצג |
|------|:---:|------|
| פעולת משתמש שנכשלה (שמירה/מחיקה/טעינה חוסמת) | כן | פער — חומרה גבוהה/קריטית |
| כשל שמלבין מסך / שובר render | כן (fallback UI) | פער קריטי |
| טעינת רקע / prefetch / אופציונלי | לא | תקין (אם נרשם) |

לכל מקור שמסווג כ"פעולת משתמש": נבדק אם בנתיב ה־`catch` יש הצגה (`showErrorWithDetails` / toast / inline / fallback) **וגם** אם ההודעה ספציפית (דרך `parseMondayError`) ולא גנרית.

---

## 6. מודל חומרה

- **קריטי** — בליעה שקטה בנתיב שמשנה נתונים (create/update/delete), או כשל לא־נתפס שעלול להלבין מסך (אין `ErrorBoundary`).
- **גבוה** — נתפס אך לא נרשם (שקוף לניטור) בנתיב קריאה; או הודעה גנרית בפעולת משתמש שנכשלה.
- **בינוני** — נרשם אך לא ברור/לא ממופה; או חסרה הצגה למשתמש בפעולה שהמשתמש יזם (לא קריטית).
- **נמוך** — קוסמטי / dev בלבד / `console` עירום / כבר מטופל אך ניתן להדק.

---

## 7. מה מחוץ להיקף (לעת עתה)

- **sink לניטור** — `logger` כותב כיום רק ל־`console`. הוספת sink חיצוני נדחית: קודם תופסים את כל השגיאות, ואז עוברים על שורות הטבלה ומוסיפים ניטור לכל אחת. הטבלה היא הכלי שהופך את זה לטריוויאלי.
