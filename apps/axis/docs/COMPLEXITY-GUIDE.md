## 1. מה זה complexity ולמה למדוד

monday מקצה לכל שאילתה "עלות" — כמה עבודה השרת עושה כדי לפתור אותה. התקציב הוא **10,000,000 נקודות לחלון של 60 שניות**. כשחורגים — הקריאה נחסמת.

אבל **המדידה שימושית הרבה מעבר ל-rate limiting**: ה-complexity הוא הכלי לכמת *איזה רכיב בשאילתה כבד באמת*, במקום לנחש. זה מה שמאפשר אופטימיזציה מבוססת-נתונים.

> **לקח מרכזי מ-Planner:** השאילתה הכבדה ביותר עלתה 12,296 — שהם **0.12% מהתקציב**. כלומר ה-complexity budget *לא* היה צוואר הבקבוק. צוואר הבקבוק היה **מבני** (קריאות בטור דרך ה-proxy), לא נפח. בלי המדידה היינו "מתקנים" את הדבר הלא נכון.

## 2. איך מודדים

מוסיפים שדה שורש `complexity` לכל קריאה — הוא מחזיר את העלות לצד הנתונים:

```graphql
query {
  complexity { before after query reset_in_x_seconds }
  boards(ids: 18401684584) {
    items_page(limit: 500) { items { id name } }
  }
}
```

| שדה | משמעות |
|---|---|
| `query` | **עלות השאילתה הזו** (זה המספר שמעניין) |
| `before` | התקציב שנותר *לפני* הקריאה |
| `after` | התקציב שנותר *אחרי* (`before - query`) |
| `reset_in_x_seconds` | מתי החלון מתאפס (תמיד ≤ 60) |

**שיטת עבודה לבידוד עלות רכיב:** מודדים את השאילתה הבסיסית, ואז מוסיפים רכיב אחד בכל פעם ומודדים שוב. ההפרש = עלות הרכיב. ככה בנינו את טבלת הפירוק בסעיף 4.

### Quirk חשוב — aliases של `boards`
שאילתה עם **שני aliases או יותר מסוג `boards`** מחזירה `complexity.query = 0` (או מספר זעיר כמו 80) באופן עקבי. זו **מגבלת-דיווח של monday**, לא קאשינג ולא שאילתה חינמית. במקרה כזה אי אפשר למדוד דרך השדה — צריך למדוד כל alias בנפרד ולחבר ידנית, או להסתמך על wall-clock.

## 4. קינון (nested) — למה הוא יקר

"קינון" = לבקש בתוך שאילתה אחת נתונים שדורשים מהשרת לפתור relations / mirrors לכל שורה. דוגמה מ-Planner: שליפת הקצאות עם המטא-דאטה של הפרויקט המקושר (`linked_items { column_values }`) ועם עמודת mirror לשעות-בפועל.

פירוק העלות של השאילתה הכבדה (12,296), רכיב-רכיב:

| רכיב | תוספת complexity | % | מה השרת עושה |
|---|---|---|---|
| גאומטריה (תאריכים, שעות, ids) | 3,424 | 28% | שדות סקלריים — זול |
| `linked_items` מקונן (מטא-פרויקט) | +4,346 | 35% | פותר relation **לכל שורה** + שולף את כל העמודות שלו |
| `BoardRelation { id name }` | +2,750 | 22% | פותר את שם הפריט המקושר |
| `MirrorValue` (שעות בפועל) | +1,480 | 12% | פותר relation אל לוח דיווחי שעות ומחשב |
| `People` | +296 | 2% | זול |

**שתי תופעות שהקינון מסתיר:**

1. **כפילות (fan-out):** מטא-הפרויקט הוא נתון ברמת ה**פרויקט**, אבל נשלף מקונן לכל **הקצאה**. 100 הקצאות על 23 פרויקטים → כל פרויקט נפתר ~4 פעמים מיותרות. ככל שיחס ההקצאות-לפרויקט גדל, הבזבוז גדל.

2. **mirror מתפוצץ עם הזמן:** עמודת mirror מסוג `sum` נראית כמו ערך אחד, אבל monday פותר את ה-relation אל **כל** השורות המקושרות. הקצאה אחת עם 70 דיווחי שעות → השרת עובר על 70 שורות, ו-`display_value` מחזיר אותן משורשרות (`"1.50, 1.50, ..."`), לא מסוכמות. **העלות גדלה עם מספר הדיווחים המצטברים, לא עם מספר ההקצאות** — זה מה שמתפוצץ בסקייל, ולא תמיד גלוי במדידה חד-פעמית.

> כלל: לפני שמסירים רכיב כבד, בדקו בקוד **מה הוא משרת**. ה-mirror, למשל, קובע את צבע הבר — אז לא ביטלנו אותו, **החלפנו את המקור** (ראו סעיף 6).

## 5. קינון מול ריבוי קריאות — שתי בעיות שונות

חשוב להבחין בין שני צירים שמתבלבלים זה בזה:

| | **complexity** (עלות חישוב) | **round-trips** (זמן רשת) |
|---|---|---|
| מה זה מודד | כמה עבודה השרת עושה | כמה פעמים הולכים ושבים |
| מי משלם | תקציב ה-10M לדקה | זמן הקיר (wall-clock), ובאפליקציית iframe גם ה-proxy |
| כשמקננים | complexity ↑↑ בקריאה אחת | round-trip אחד |
| כשמפצלים לקריאות | complexity ↓ בכל קריאה | round-trips ↑↑ |

**התובנה:** אלה לא אותה בעיה. בקצה האחד — קינון אגרסיבי לקריאה ענקית אחת (complexity גבוה). בקצה השני — לולאת N קריאות נפרדות (N round-trips). **שני הקצוות גרועים.** הנקודה האופטימלית באמצע.

### למה ריבוי קריאות נפרד כל-כך יקר ב-Planner
ה-SDK של monday עובד דרך **proxy** ב-iframe. כל קריאה נפרדת סופגת **קפיצת proxy** משלה, וה-proxy **מסדרֵת** קריאות נפרדות (גם כש-`Promise.allSettled` אמור להריץ אותן במקביל). מדדנו בדפדפן: ~6 קריאות סדרתיות = **~21 שניות** waterfall. זה היה צוואר הבקבוק האמיתי — לא ה-complexity.

### האנטי-פטרן הגרוע מכולם
לולאת "לכל הקצאה, שלוף את השעות שלה" = N round-trips. זה **גרוע יותר** מ-mirror יקר בקריאה אחת. לעולם אל תפתרו fan-out עם לולאת קריאות.

## 6. הכלל המעשי: קונסולידציה, לא פיצול ולא קינון

הפתרון שהגענו אליו ב-Planner — **לא** "להריץ במקביל" (ה-proxy יסדר בכל זאת), אלא **לאחד למסמך GraphQL אחד** את כל מה שבלתי-תלוי, ולהוציא מהשאילתה הכבדה את הרכיבים שאפשר להחליף במקור זול:

```graphql
query {
  # קריאה מאוחדת אחת = round-trip אחד = קפיצת proxy אחת
  allocations: boards(ids: ALLOC) {
    items_page(limit: 500) {
      items { id ... גאומטריה רזה + board_relation { linked_item_ids } }   # ~3,128
    }
  }
  employees: boards(ids: EMP) { items_page { items { ... } } }              # ~140
  cols:      boards(ids: ALLOC) { columns { id title settings_str } }       # ~31
  reported:  aggregate(...)     # SUM שעות GROUP BY ID(relation) → Map      # ~122
}
# ואז join ב-JS לפי id (לא לפי שם)
```

מה השתנה ולמה זה עובד:

| בעיה מקורית | הפתרון | רווח |
|---|---|---|
| mirror יקר (פותר 70 דיווחים/הקצאה) | `aggregate` עם `SUM ... GROUP BY ID(relation)` — מסוכם **בשרת**, קריאה אחת לכל ההקצאות | mirror +1,480 + פתירה כבדה → ~122 |
| `linked_items` מקונן למטא-פרויקט (fan-out ×4) | `linked_item_ids` בלבד (כמעט חינם) → distinct projectIds → `items(ids:[...])` פעם אחת לפרויקט | +4,346 +2,750 → ~זניח |
| 6 קריאות בטור דרך proxy | מסמך GraphQL אחד, round-trip אחד | ~21s → ~3–4s |

**תוצאות מדודות (PoC):** השאילתה הקריטית ירדה מ-~12,300 ל-~3,130 complexity; שכבת ה-API ירדה מ-7,575ms ל-3,151ms (**×2.4**, ובדפדפן יותר כי כל round-trip חוסך קפיצת proxy). first-paint מוערך ~29s → ~10–11s.

## 7. checklist לאופטימיזציה מבוססת-complexity

1. **מדוד את המצב הקיים** ב-DevTools (waterfall) — פעמיים, לוודא שזה לא רעש רשת.
2. **בודד מקור:** האם הקריאות בטור באשמת האפליקציה (await/useEffect) או ה-framework? (כמעט תמיד האפליקציה.)
3. **כמת כל חשד** עם שדה `complexity`, רכיב-רכיב — אל תניח מה כבד.
4. **בדוק בקוד מה כל רכיב כבד משרת** לפני שמסירים אותו.
5. **החלף מקור, לא פיצ'ר:** mirror→aggregate, קינון→ids+items נפרד.
6. **אחד לקריאה אחת** את הבלתי-תלוי (round-trip יחיד), במקום להריץ "במקביל".
7. **ג'וין לפי id, לעולם לא לפי שם** (ראו [[prefer-id-over-name-for-joins]]).
8. **PoC מדיד** (wall-clock + complexity, cold/warm) לפני שמממשים.
